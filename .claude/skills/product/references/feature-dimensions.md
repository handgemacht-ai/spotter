# Feature Planning Dimensions

Product-level guidance for which dimensions to explore when planning features.
Generated by deep-dig-feature, updated as the product evolves.

## Always Probe

### Problem & Motivation
- Spotter is a developer tool — features must solve a real workflow pain, not add polish for polish's sake
- Key questions: What's the struggling moment? What workaround exists today?

### Scope & Boundaries
- Solo dev with limited time — appetite matters. Every feature competes with shipping product features in the rigs
- Key questions: What's the appetite? What's in/out? What's deferred?

### Interaction Model & States
- LiveView UI with async data loading from Dolt/SQLite — every view needs loading, empty, error, and data states
- Key questions: All UI states? Loading behavior? Error display?

### Data Model & Lifecycle
- Two data backends (SQLite via Ash, Dolt for beads) with different query patterns and timeout characteristics
- Key questions: Which backend? New entities? Query strategy? N+1 risk?

### Integration & Ecosystem
- Features touch beads, Dolt, git, OTEL, and the plugin — changes ripple across boundaries
- Key questions: What existing views/services are affected? Does the plugin need updates?

### Feasibility & Technical Risk
- Dolt queries have 2s timeouts. OTEL tracing is mandatory. GitRunner is the only git interface
- Key questions: Performance at scale? Dolt query complexity? New dependencies?

## Probe When Relevant

### Operational Readiness
- Trigger: Feature involves background jobs, Dolt queries, or OTEL spans that agents need to introspect/debug
- Key questions: What spans? What does agent debugging look like?

### Error Handling & Failure Modes
- Trigger: Feature depends on Dolt (can be down) or external services
- Key questions: Dolt down behavior? Timeout handling? Graceful degradation?

### Documentation & Learnability
- Trigger: Feature changes agent-facing APIs or MCP tools
- Key questions: Does the plugin need updates? MCP tool changes?

## Not Applicable

### User Segments
- Why: Always solo developer
- Revisit when: Multi-user support is added

### Permissions & Access
- Why: Localhost prototype, no authentication
- Revisit when: Authentication is added

### Abuse Risk
- Why: Localhost only
- Revisit when: Network-accessible deployment

### Business Viability
- Why: Internal tool / prototype
- Revisit when: Considering commercialization

### Notifications
- Why: Single user, synchronous UI
- Revisit when: Async workflows or multi-user

### Competitive Context
- Why: Unique internal tool
- Revisit when: Similar tools emerge

### Migration & Rollout
- Why: Single user, localhost — just ship it
- Revisit when: Multi-instance or shared deployment

### Analytics & Measurement
- Why: No feature usage instrumentation needed (plugin has its own)
- Revisit when: Usage data becomes valuable for product decisions
